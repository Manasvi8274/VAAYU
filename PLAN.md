# Personal "Jarvis/Friday"-style AI Assistant — Plan

## Context

The user wants to build a personal AI voice assistant, in the spirit of Jarvis/Friday from Iron Man, for their own Windows 11 laptop and (later) their own Android phone. This is a from-scratch build in an empty repo (`C:\Users\manu1\Documents\GitHub\TEST` currently has only `README.md` + `.gitattributes`). The motivation is twofold: a genuinely useful personal automation tool, and a standout portfolio/resume project — the user explicitly wants to learn full-stack/AI-systems fundamentals by building it incrementally, not have a black box handed to them.

Research (via two background agents) established the realistic ceiling of what's possible:
- **Windows, as the logged-in user**: essentially everything a movie-Jarvis does — files, launching/closing apps, input simulation, screen capture, clipboard, mic/webcam, system settings, notifications, browser automation — is achievable with no elevation. Admin adds registry/service/install control. Hard walls (even as admin) only matter for *other users'* protected secrets (DPAPI, Windows Hello, Credential Guard) — irrelevant for a single-user personal assistant on your own account.
- **Android, sideloaded on the user's own phone**: **Accessibility Service** is the core "remote control" API (reads any app's screen, simulates taps/typing anywhere) — covers ~80% of real control. The user chose to also use **Shizuku** (ADB-shell privilege, no root) for silent app install/uninstall and permission automation. **Full root was explicitly rejected** — it wipes the phone, breaks banking/Wallet apps, and needs constant maintenance to hide from Play Integrity checks. Not worth it for a daily-driver phone.
- **Critical safety point from research**: once access is granted, the OS does not limit what the assistant does with it — an assistant with input-injection/screen-reading can do anything the user could do, including inside banking apps. The user confirmed: **sensitive actions must always require explicit confirmation**, even once everything is fully set up and trusted. This is a permanent design rule, not a v1-only stopgap.

**Staging the user agreed to**: plan now, build later, and when building: **PC assistant first (Phase 1)**, **Android companion later (Phase 2)** — not simultaneously. This plan covers Phase 1 in full implementation detail and Phase 2 at scoping/architecture-seam level only.

## Phase 1: Windows PC Assistant (build this first)

### Stack & library choices

| Component | Choice | Why |
|---|---|---|
| LLM brain | `ollama` Python client, default model **qwen2.5:7b-instruct** (fallback **qwen2.5:3b**/`llama3.2:3b` if the machine is slow) | Local, free, private; qwen2.5 has solid tool-calling support at a size realistic for a personal PC (CPU or modest GPU). 70B+ models aren't practical here. |
| Wake word | **openWakeWord** (stock "hey jarvis" keyword) | Free, open-source, fully offline (ONNX), no API key/online check-in — unlike Picovoice Porcupine, which needs a periodic online key check. |
| Hotkey / media keys | `keyboard` package | One dependency covers global push-to-talk hotkey (fallback activation mode) and OS media-key simulation. |
| STT | **faster-whisper** (`base.en`/`small.en`, `int8`) | ~4x faster than `openai-whisper`, runs well CPU-only, no separate ffmpeg install. |
| TTS | **pyttsx3** (v1, wraps Windows SAPI5) → **Piper TTS** (later swap-in upgrade) | pyttsx3 = zero setup, instant working pipeline for early milestones. Piper = much more natural voice, added later behind a shared `TTSEngine` interface so swapping is a config change, not a rewrite. |
| Speaker verification (voice lock) | **Resemblyzer** | Small, quick install, enroll via ~20-30s sample, cosine-similarity match. **Must be communicated as personalization-grade, not cryptographic security** — a recording or cloned voice could plausibly fool it; it must never gate anything sensitive by itself. |
| App launcher | **AppOpener** | Fuzzy open/close of Windows apps by name; first call does a one-time index scan (a few seconds — expected, not a hang). |
| System info | `psutil` | CPU/RAM/battery/disk. |
| Audio I/O | `sounddevice` + `numpy` | Easier Windows install than PyAudio (no build toolchain needed). |
| Notes storage | stdlib `sqlite3` | Zero extra dependency, real DB pattern, room to grow. |
| Config | `pydantic` + `PyYAML` | Typed, validated `config.yaml` instead of scattered magic values. |

### Tool-calling pattern & safety rule (applies to ALL future tools, PC and Android)

- `tools/registry.py`: `@tool` decorator registers each Python function with name/description/JSON-schema, exposes `get_ollama_tools()` (OpenAI-style schema Ollama accepts) and `dispatch(name, args)`.
- Two-pass flow per turn: send transcript + tool schemas to the model → if `tool_calls` returned, dispatch and feed the result back → second call produces the final spoken reply. Cap at **one tool call per turn** in v1 (small local models are less reliable at chained multi-tool reasoning).
- **Permanent safety rule**: every tool has a `requires_confirmation: bool` flag. Any tool touching a sensitive category — **finance/payment apps, credential managers, 2FA/OTP, sending messages/communications on the user's behalf, deleting/destructive file operations, installing/uninstalling software** — must set this `True`. When set, the orchestrator speaks a confirmation prompt and requires an explicit affirmative reply before dispatching. This flag exists in the registry from day one, even though v1's tool set doesn't need it yet.
- **v1 tool set (all non-destructive, `requires_confirmation=False`)**: `get_system_status`, `open_app`, `close_app`, `control_media`, `open_website`, `search_files`/`read_file` (scoped to safe roots: Desktop/Documents/Downloads by config), `add_note`/`list_notes`.
- **Explicitly excluded from v1** (future, confirmation-gated when added): delete_file, arbitrary shell/code execution, installing software, changing system security settings, sending messages/emails.

### Runtime flow (updated: continuous listening replaced hotkey push-to-talk as the default)

User explicitly wanted hands-free operation (no per-turn manual trigger) instead of the original hotkey design, so M3 was rebuilt around continuous voice-activity-based listening. Hotkey mode is kept available via `activation.mode: "hotkey"` but is no longer the default. M4 (speaker verification) is **postponed** until this is solid.

1. Startup loads `config.yaml`, starts a persistent microphone stream (`VADListener.start()`, which also calibrates the room's ambient noise floor), builds STT/TTS engines, Ollama client, tool registry.
2. Idle: mic stays open continuously; utterances are auto-segmented by voice activity (see below) rather than waiting for a hotkey.
3. STT transcribes (with built-in filtering to reduce - not eliminate - hallucination on noise, see Known limitations); empty/low-confidence → silently return to listening.
4. LLM call with tools → dispatch tool if requested (with confirmation step if flagged) → second LLM call for final reply.
5. Capture is muted → TTS speaks the reply (so the mic can't hear the assistant's own voice) → unmuted → back to listening automatically, hands-free.

**Utterance segmentation (`assistant/audio/vad_listener.py`)**: a frame is only treated as candidate speech if it passes *two* independent checks - `webrtcvad` classification AND an energy/RMS floor calibrated from ~1s of ambient room audio at startup (`energy_threshold_multiplier` × measured noise floor). This combination was necessary: webrtcvad alone was tested and found to misclassify this room's ambient noise as speech even at its strictest setting. A run of `silence_duration_ms` (default 900ms) of non-speech ends the utterance.

**Two non-obvious bugs found only through real end-to-end testing (see also Known limitations):**
- Opening a fresh `sd.InputStream` per utterance (instead of once for the session) had an intermittent startup race that could truncate the very next utterance right after the assistant finished speaking. Fixed by keeping one persistent, callback-based stream open for the whole session instead of per-turn.
- `pyttsx3` reusing one engine instance across multiple `speak()` calls plays real audio on the *first* call only - later calls complete with no error but produce no audible output (confirmed via mic RMS: ~3-5 vs ~600-2000+ for real speech). Fixed by creating a fresh engine per call (`tts/pyttsx3_engine.py`).

### Setup steps outside of code (user does these manually — cannot be done from this session)

1. Install Python 3.11/3.12 (64-bit), add to PATH.
2. Install Ollama for Windows (runs as local service on `localhost:11434`).
3. `ollama pull qwen2.5:7b-instruct` (+ optional smaller fallback); verify with `ollama list`.
4. Windows Settings → Privacy & security → Microphone: enable, and enable "let desktop apps access microphone."
5. Install VC++ Redistributable if any audio-related pip wheel fails.
6. `python -m venv .venv` + activate (PowerShell execution-policy fix if blocked: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`).
7. `pip install -r requirements.txt` once it exists (note: Resemblyzer pulls in `torch`, ~2GB).
8. At the Piper milestone: manually download the chosen Piper voice files into `models/piper/`.
9. Enrollment (M4): run `python -m assistant.speaker_id.enroll`, speak for ~20-30s.

### Incremental build order

- **M0 — Scaffolding**: repo structure, venv, `requirements.txt`, `config.yaml`, `scripts/setup_check.py`. No AI code yet.
- **M1 — Text-in/out brain + one tool**: terminal input loop → Ollama → registry with only `get_system_status`. Proves tool-calling works before adding voice complexity.
- **M2 — Full v1 tool set**: add `open_app`, `control_media`, `open_website`, `search_files`/`read_file`, notes. Still text-based; add `tests/test_tool_registry.py`.
- **M3 — Real voice I/O**: rebuilt from hotkey-triggered capture to hands-free continuous listening (voice-activity-segmented, no manual trigger) per an explicit user request - "I want to fully control [it] via voice," not press-and-speak. Hotkey mode kept as a config fallback. This is the milestone that "feels like Jarvis."
- **M4 — Speaker verification**: **postponed** by explicit user request, until continuous listening is solid. Original plan: enroll/verify gate inserted before STT.
- **M5 — Hands-free wake word**: openWakeWord activation, `activation_mode` config toggle (hotkey stays available as fallback).
- **M6 (polish)**: Piper TTS upgrade behind the `TTSEngine` interface; debug logging; `interfaces/remote_api.py` stub added (interface + docstring only) as the seam for Phase 2.

### Known limitations to expect (not blockers, just realism)

- Local 7-8B tool-calling is noticeably less reliable than cloud Claude/GPT — occasional wrong tool choice or malformed args.
- **No wake word without a manual trigger means the assistant can't distinguish "the user talking to it" from any other audio in the room — confirmed in testing, not just theoretical.** A video/audio source playing nearby got transcribed and treated as a real command; muting it dropped the false-trigger rate to zero in the same test. STT-side mitigations (`vad_filter=True`, a minimum-word-count check) reduce hallucination on genuine silence/noise, but can't distinguish real-but-irrelevant audio from a real command. M5 (wake word) is the actual fix for this, not something arguable further with more STT tuning.
- Speaker verification is a convenience filter, not security (once M4 resumes).
- CPU-only latency: several seconds of "thinking" time per turn is realistic without a GPU.
- The original hotkey design's global hook (`keyboard` library) received zero events in testing without Administrator rights - replaced with the Win32 `RegisterHotKey` API for the (now-secondary) hotkey mode, which works without elevation.
- **Dictation (`type_text`, added post-M3)**: initially implemented with `keyboard.write()` (character-by-character simulated keystrokes) - tested and found to corrupt text typed into Windows 11's Notepad (a modern WinUI3/XAML-based control), dropping/repeating characters faster than the control could keep up. Fixed with clipboard + Ctrl+V (one atomic paste) instead, which is also more broadly compatible across classic and modern text controls. Verified by reading the actual control's text back via its real (nested, non-obvious) window handle, not just trusting the tool call succeeded.
- **Utterance-start clipping, fixed with a pre-roll buffer**: a short/soft-onset trigger word (e.g. "type") could fall below the speech-detection threshold for its first ~100-200ms and get dropped from the transcript entirely. Fixed by keeping a rolling ~300ms lookback buffer that gets prepended once speech is confirmed (`VADListener.preroll_frames`, config: `listening.preroll_ms`). Even after this fix, testing surfaced a separate, real speech-recognition limitation: Whisper can mishear a short word for a similarly-sounding one (e.g. "type" → "Time") - worse via synthesized-TTS-through-speaker test audio than real human speech is likely to be, but a real accuracy ceiling of the small `base.en` model, not a capture bug.
- **App-name/vocabulary recognition (user report: "whatsapp" needed ~5 attempts, then a follow-up request to "fix most misunderstood words in general")**: root-caused via controlled comparisons, not guessing.
  - First pass: reproduced "open whatsapp" being misheard as "Open what's up?"/"Open what's that?" reliably. Tested `base.en` → `small.en` (barely changed the result) vs. a vocabulary hint (`initial_prompt`) - the hint was decisive on both model sizes, so model size wasn't the bottleneck.
  - Second pass (broader fix): expanded `_VOCAB_PROMPT` substantially (more app names incl. common Indian-context apps - PhonePe, Paytm, Swiggy, Zomato, etc. - plus general command vocabulary) and tested across 10 varied commands on both model sizes, all with the expanded hint. Result: `base.en` matched or beat `small.en` across the board (`small.en` actually regressed on one phrase, "reduce the volume" → "Here's the value") - confirms `base.en` + a good vocabulary hint is the right default, not a bigger model.
  - One word ("Paytm") resisted the hint even after expanding the list and adding an emphasis sentence - only *repeating the word several times* in the prompt fixed it in isolated testing. Repeating every word that heavily isn't practical (untested whether it would dilute the hint's effect on everything else), so this is documented as a known remaining limitation rather than force-fixed; add targeted repetition for a specific word if it keeps failing in practice.
  - Also confirmed (via a raw-audio duration check) that an apparent "take a screenshot" → "screenshot." failure during the broad test was one-off ASR variance, not a systematic clipping bug - the same phrase transcribed correctly on two immediate re-tests with identical capture code.
- **Hinglish support ("whatsapp open kro")**: switched `stt/whisper_stt.py`'s default model from `base.en` to the multilingual `base` (English-only models cannot produce Hindi/Hinglish tokens at all, by construction), kept `language="en"` to keep output in Roman script rather than Devanagari, and added common Hinglish command words (kro, karo, kholo, kitni, band karo, etc.) to `_VOCAB_PROMPT`. Both settings are now configurable (`STTConfig.whisper_model_size`, `STTConfig.language`) so they can be tuned without a code change. Also updated `SYSTEM_PROMPT` to explicitly tell the LLM the user may speak Hinglish, since qwen2.5 likely handles code-mixed intent better than exact-phrase matching would.
  - **This could not be properly validated**: there is no Hindi voice or Windows language pack installed on the dev machine, so realistic Hindi/Hinglish pronunciation could not be tested - an English SAPI5 voice mispronouncing Hindi words (e.g. "kro", "kitni hai") produces audio garbled enough that neither language setting nor auto-detect could parse it ("battery kitni hai" → "Battery keyed me hot." across the board). This is a genuine testing-capability limit, documented rather than papered over with a misleading "verified" claim - real validation needs the user's actual voice.
  - What WAS validated: a controlled same-audio comparison of `base.en` vs. multilingual `base` across 8 English phrases showed no clear accuracy cost to the multilingual switch (multilingual actually scored slightly better in that run, 6/8 vs 4.5/8) - the noise in both was attributed to general TTS-loopback test degradation over a long session, not the model swap, so multilingual `base` was kept as the default with reasonable confidence English recognition isn't harmed.
- **Assistant named "Vaayu" + Sleeping/Awake/Shutdown state machine + auto-start at login** (explicit user request, replaces the plain always-on continuous-listening design from earlier in M3):
  - New `assistant/control_phrases.py` detects "wake up Vaayu"/"sleep Vaayu"/"shutdown Vaayu" via keyword matching (both a control word AND the name "Vaayu" - or "Vayu", see below - must be present), not exact-phrase matching, since STT output for a short command varies run to run. Deliberately requires the name alongside the control word so ordinary conversation ("I need to sleep soon") can never accidentally change the assistant's running state - verified with unit tests covering exactly that false-positive case (`tests/test_control_phrases.py`).
  - `Orchestrator` gained a `State` enum (SLEEPING - the boot state - and AWAKE). While SLEEPING, every utterance is still transcribed (has to be, to catch the wake phrase) but only wake/shutdown commands are acted on; real commands are silently ignored. Shutdown works from either state. Fully verified end-to-end with real voice across all 6 transitions (ignored-while-asleep → wake → processed-while-awake → sleep → ignored-while-asleep-again → shutdown), not just the phrase-matching unit tests in isolation.
  - **"Vaayu" recognition itself could not be made reliable in testing** - unlike "WhatsApp" (fixed) or even "Paytm" (fixed via repetition), no vocabulary-hint variant tried (single mention, 3x repetition, repetition + phrase, alternate spelling) got Whisper to output anything resembling "Vaayu"/"Vayu" from the TTS-synthesized test audio - it consistently produced unrelated words ("baby", "demon", "dream"). Strongly suspected to be a TTS pronunciation problem specific to this Sanskrit-origin word (same category as the Hinglish testing limitation above) rather than a fixable prompt/STT issue, but this is *not confirmed* - it needs the user's real voice to properly diagnose. Shipped anyway with `control_phrases.py` accepting both "Vaayu" and "Vayu" spellings as a no-cost robustness margin, and documented as an open issue (README) rather than claimed as working.
  - Fixed two real bugs discovered while setting up auto-start, both confirmed via direct testing, not assumed:
    1. `load_config()` defaulted to the relative path `"config/config.yaml"`, which only resolves when the working directory happens to be the repo root (true for every manual run so far, since the README always says to run from the repo, but not guaranteed for a process launched by Task Scheduler). Fixed by resolving relative to `config_schema.py`'s own file location (`Path(__file__).resolve().parent.parent`) when no explicit path is given.
    2. `pythonw.exe` (needed for a no-console background launch) was suspected, then confirmed via direct testing, to give the process `sys.stdout = None` - the very first `print()` call would otherwise crash with `AttributeError`, silently killing the assistant on every boot with no diagnostic. An initial ad-hoc test via git-bash's `pythonw.exe` invocation showed a *real* stdout (because git-bash provides its own pipe plumbing, not representative of a true parentless launch) - so this was re-verified against the *actual* Task-Scheduler-launched process, which did show `sys.stdout is None` and did need the fix. New `assistant/log_setup.py`'s `ensure_output_stream()` redirects stdout/stderr to `data/vaayu.log` only when `sys.stdout is None`, leaving normal terminal runs unaffected.
  - Auto-start registered via PowerShell's `Register-ScheduledTask` (not the legacy `schtasks.exe` CLI, which doesn't cleanly expose a working-directory option) - trigger `AtLogOn` for the current user, action = `pythonw.exe -m assistant.voice_main` with `-WorkingDirectory` set to the repo root (needed for Python's `-m` module resolution, which adds the *current working directory*, not the target file's location, to `sys.path`). Verified end-to-end for real: registered the task, manually triggered it, confirmed via `data/vaayu.log` that it started cleanly in the SLEEPING state, then confirmed it was genuinely listening by speaking "wake up Vaayu" at the real running background process (not a manual test script) and observing the log.
- **Combined "Vaayu, open brave" wake+command flow** (explicit user request - originally only a bare "wake up Vaayu" with no attached command was supported): `control_phrases.py` gained `is_name_mentioned()` (broader than `is_wake_command` - true whenever the name is said, regardless of "wake") and `has_command_content()` (true if there's meaningful text beyond wake-filler words like "wake"/"up"/"vaayu"). While SLEEPING, if the name is mentioned: wake up, and if there's command content beyond just the name, fall through to normal LLM processing in the *same turn* rather than requiring a second listening cycle. `SYSTEM_PROMPT` updated to tell the LLM the name may appear as a vocative prefix, not part of the actual request. Verified correct with the transcript controlled directly (STT mocked to return "vaayu open brave") since real recognition of "Vaayu" remains unverified (see above) - confirmed: SLEEPING -> AWAKE transition + a real `open_app("brave")` tool call, both in one `handle_one_turn()` call.
- **Brave/browser tool-selection bug** (user report: "open the brave browser" opened Chrome and searched "brave" instead of launching Brave) - root-caused via a false-alarm detour first, then the real fix:
  - **False alarm, documented as a lesson**: initial diagnostics appeared to show `OllamaBrain.respond()` never calling any tool at all for *any* command, even "what's my battery percentage" (100% reliable all session). Dug down to a raw `ollama.chat()` call (bypassing all wrapper code) to isolate the cause - which worked fine, as did the full real `SYSTEM_PROMPT` and all 17 real tool schemas via a raw call. The actual bug was in the *test scripts themselves*: `ollama`'s response message is a `Message` object, not a plain `dict`, and the diagnostics gated extraction on `isinstance(x, dict)`, which silently evaluated `False` for real, successful tool-calling responses - producing `None` regardless of whether a tool call happened. Confirmed the real production code was never broken by checking actual side effects (real tool dispatch, real system data in the tool result message). Lesson: `Message` objects support `.get()` directly (duck-typed dict-like access) - check for that capability (`hasattr(x, "get")`), not `isinstance(x, dict)`.
  - **The real bug**: reproduced cleanly once the diagnostic was fixed - "open the brave browser" called `open_website(url_or_query="brave")` (searches, wrong tool) while "open brave application" correctly called `open_app(app_name="brave")`. The word "browser" was biasing the model toward `open_website` over `open_app`. Fixed by making both tool descriptions explicitly disambiguate this (`open_app`: "...launching a web browser itself by name - 'chrome', 'brave', 'firefox', 'edge' are applications, not websites"; `open_website`: "Do NOT use this to launch a browser application by name..."). Re-verified: all three tested phrasings ("open the brave browser", "open brave", "open brave application") now correctly call `open_app`.
- **General browser targeting for `open_website`** (explicit follow-up request: the fix above only helped `open_app` pick the right tool - a *second*, deeper bug remained: `open_website` always used `webbrowser.open()`, which goes to the OS default browser regardless of what's actually open, so "open brave" then "open youtube" opened Brave then silently sent YouTube to Chrome instead). User explicitly asked this be general, not hardcoded to Brave specifically (e.g. Opera should work too, without needing to know about Opera in advance). New `tools/browser_state.py`:
  - Enumerates Windows' own `HKCU`/`HKLM` `SOFTWARE\Clients\StartMenuInternet` registry (the same list Windows' "choose your default browser" Settings page reads from) via stdlib `winreg` - no hardcoded browser list. Verified this finds browsers that wouldn't have been anticipated: on the dev machine, it found "Comet" (Perplexity's browser) alongside Chrome/Brave/Edge.
  - Resolution order for which browser to target: (1) the one Vaayu itself most recently opened via `open_app` this session, (2) whichever registered browser currently owns the OS foreground window (via the same `win32gui`/`win32process`/`psutil` combination used elsewhere in the project), (3) any registered browser with a running process at all, (4) none found -> caller falls back to `webbrowser.open()` (OS default), same as before this fix.
  - Verified end-to-end for real, not just unit-level: opened a browser *manually* (not via Vaayu's `open_app`, simulating "user already had it open") with `_last_browser_name` unset, confirmed the fallback detection correctly targeted it. Then, with two browsers running simultaneously, explicitly switched focus to one and confirmed the *foreground* one was targeted over the other, not just "any running browser" - real disambiguation, not a lucky single-browser-only test.
- **Status orb** (explicit user request - "colored ball on the top left corner ... glow and match to the vaayu voice ... like Siri"): new `assistant/gui/status_orb.py` (Tkinter, stdlib - no new dependency) and `Pyttsx3Engine.speak_with_amplitude()`.
  - pyttsx3 doesn't expose real-time playback amplitude (it drives SAPI5 directly), so a genuinely voice-reactive glow needed restructuring TTS playback: synthesize to a temp WAV first (`save_to_file`, already used elsewhere), then play it via `sounddevice.play()` instead of pyttsx3's own playback, sampling real RMS amplitude in ~30ms chunks during playback and reporting it via a callback. Verified standalone first: 111 real amplitude samples over one utterance, ranging 0.0 to 0.21, tracking real speech dynamics (not synthetic/generic).
  - Threading: Tkinter's `mainloop()` must run on the main thread and only that thread may touch its widgets, so `voice_main.py` now runs the orchestrator (listening/thinking/speaking) on a background thread instead, communicating via a `queue.Queue` that the orb polls every 30ms via `root.after()` - the standard safe pattern for this.
  - **Cosmetic limitation, honestly documented rather than silently shipped**: attempted a true circular floating look via Windows' `-transparentcolor` window attribute (several standard orderings/recipes tried), but it did not visibly take effect in testing - confirmed via screenshot (`PIL.ImageGrab`, installed temporarily for verification only, not a project dependency), showing a solid dark square behind the circle instead of transparency. Unclear whether this is a genuine Tk/Windows compositing limitation or specific to how screenshots capture layered windows - not resolved, but the fallback (small dark square panel) is not broken, just not as polished as intended.
  - **The actual point of the widget - reacting to real voice** - fully verified end-to-end, not just standalone: ran the real orchestrator pipeline (wake command -> real LLM tool call -> real `speak_with_amplitude`) with dense pixel-sampling of the orb during the whole turn, confirmed the color visibly brightened (from idle `(43,58,85)` to `(53,162,215)` at peak) exactly while real speech was playing, then returned to idle after. An initial pass with coarser, less frequent sampling appeared to show no glow at all - traced to sampling-loop timing relative to the LLM's variable processing delay, not a real bug; re-verified with denser sampling to confirm.
- **Foreground/background window control** (explicit user request - "if brave opened, currently the brave opened in the background but it should open in foreground"): root cause was the *same* Windows foreground-lock issue already solved once for `switch_to_window` (a background process can't just call `SetForegroundWindow` and have it work) - just not applied to `open_app`/`open_website` yet. Refactored the fix into a shared `tools/window_utils.py` (`force_foreground`, `foreground_by_title` with retry since a just-launched window may not exist yet the instant the launch call returns) and wired it into both, gated by a new `foreground: bool = True` parameter (both tools' descriptions tell the model to only pass `false` when the user explicitly says "in the background"). Verified for real, both directions: opened Brave, switched focus away, sent it a URL, confirmed it came back to foreground; separately confirmed `foreground=False` does NOT steal focus from another window.
- **Real browser page interaction** (`browser_automation.py`: `browse_to`, `read_page`, `click_on_page`) - added so multi-step "open the channel, click the video" style requests could actually be followed through, not just searched. Uses the Chrome DevTools Protocol's WebSocket interface (`Page.navigate`, `Runtime.evaluate`), not just the HTTP endpoints `browser.py` already used for tab listing - new dependency `websocket-client`. Found and worked around a real setup gap during testing: newer Chromium versions reject the WebSocket handshake with 403 unless launched with `--remote-allow-origins=*` in addition to `--remote-debugging-port=9222` - not needed for the HTTP-only tab tools, only for this WebSocket-based control; not documented anywhere obvious, found by hitting the actual error. Verified for real against live YouTube: searched, read the page, clicked a channel result (real navigation to `youtube.com/@theogcrewofficial` confirmed via URL), clicked a video title from that page (real navigation to the correct `watch?v=` URL confirmed).
- **Multi-step tool calling** (`ollama_client.py`): upgraded from a hard one-tool-call-per-turn cap to a loop capped at 5 steps, so a single command can chain read_page -> click_on_page -> read_page -> click_on_page -> final reply instead of needing a separate command per step. Necessary once page-interaction tools existed at all, but **testing showed this alone was not sufficient**: given the same task and even a very explicit step-by-step recipe in the system prompt, the 3B model repeatedly failed to actually plan the sequence correctly - hallucinating fake URLs (`youtube.com/c/OGCrewVideos`, `brave.com/youtube`), reaching for unrelated tools (`control_media`, `switch_to_browser_tab`) instead of `click_on_page`, and in one run falsely claiming success ("Now playing...") after none of the real steps worked. This is a genuine model-capability limit, not a prompt-wording problem - see the next entry for the actual fix.
- **YouTube composite tools** (`tools/youtube.py`: `play_latest_video_from_channel`, `play_video_on_youtube`) - the real fix for the multi-step planning failure above: instead of relying on the weak model to correctly sequence 4-5 tool calls, these do the whole search -> extract -> navigate chain deterministically in Python, so the model only has to make one simple, reliable tool choice (matching its demonstrated strength - single correct tool + argument selection has been reliable all session - rather than its demonstrated weakness in multi-step planning).
  - DOM extraction was also tested and corrected, not guessed: an initial version using YouTube's internal custom element tags (`ytd-video-renderer`, `ytd-rich-item-renderer`) worked on search-results pages but returned nothing on a channel's home page - inspected the live DOM and found the home page uses different, less predictable internal structure. Switched to a generic `a[href*="/watch?v="]` selector, which works consistently across page layouts.
  - Also found and fixed a correctness bug beyond the selector issue: a channel's plain home page can show a *pinned/featured* video (via `ytd-channel-video-player-renderer`) that is NOT necessarily the newest upload - confirmed this directly (home page's first video link differed from the actual newest one). Fixed by navigating to the channel's dedicated `/videos` tab specifically, which is sorted with the newest first - verified the resulting URL exactly matched the video independently confirmed correct via manual `click_on_page` testing earlier.
  - Re-verified through the actual LLM afterward (not just direct dispatch): "play the latest video from the OG Crew channel", "play some hollywood songs on youtube", and "play the song Perfect by Ed Sheeran" all correctly called the new composite tools with sensible arguments - a large reliability improvement over the failures above.
- **Status orb v2** (explicit follow-up requests - "colorful ... like SIRI ball", "raggable with the cursor", voice-controlled repositioning): idle state now continuously cycles hue in a cyan -> blue -> purple -> pink triangle wave (Siri's actual palette, not the full rainbow - an initial full-hue-wheel version was visibly less authentic and was narrowed after review) instead of a static dim color; `_HUE_CYCLE_SECONDS` speeds up while speaking for a more "alive" look. Draggable via standard Tkinter `<ButtonPress-1>`/`<B1-Motion>` bindings. New `gui/orb_position.py` (pure, unit-tested function) parses spoken position/direction text into screen coordinates - distinguishes an absolute named position ("center", "top right") from a relative nudge ("a little left") by the presence of a magnitude word, not by requiring an exact phrase. New `gui/orb_bridge.py` lets the `move_status_orb` tool (which has no direct access to the Orchestrator/queue) reach the orb from a plain tool function. Verified for real: captured idle frames ~2s apart showing genuinely different colors within the intended palette (not the earlier full-rainbow version), and confirmed the position math for both an absolute move ("center" -> exact expected screen coordinates for this machine's resolution) and a relative nudge ("a little left" -> exactly -40px from wherever it was).
- **Safety incident, documented rather than glossed over**: a bulk test that opened then closed several real applications (to verify `open_app`/`close_app` broadly) closed the user's own already-open Visual Studio Code window - `close_app` (via AppOpener) matches by process/app name with no way to distinguish "the instance I opened for this test" from "the instance you were already using for real work." The user asked directly why VS Code closed; confirmed the mechanism, apologized, and stopped the broader open/close sweep rather than continuing to test `close_app` against applications that might be holding someone's active work. Documented as a explicit warning in the README rather than only handled in-conversation, since it's a real, repeatable risk of this tool, not a one-off fluke.
- **Status orb v3 - marble sphere, rotation as the sleep/awake signal** (explicit follow-up request, with a reference image link that couldn't actually be fetched - Pinterest board/"ideas" pages are JS-rendered collections, not a single fetchable image; built from a standard understanding of the glass-marble aesthetic instead, disclosed as such rather than pretending the reference was used). Rebuilt `status_orb.py`'s rendering: a radial-gradient base (concentric `create_oval` rings, cyan center -> pink edge) with `_STREAK_COUNT` colored `create_arc` pie-slice wedges layered on top (their `start` angle updated every frame to animate), plus a fixed white stippled highlight oval for a 3D-sphere illusion - chose native Tkinter pie-slice arcs over hand-rolled polygon/point math for the rotating wedges specifically because it's far simpler and more robust (just update one `start` parameter per frame) while still reading as a genuine swirl once layered over the gradient rings.
  - **Rotation is now the actual sleep/awake indicator** (a semantic change from v2, which only reacted to speaking, not sleep state at all): `Orchestrator` gained `_set_state()`, pushing `{"kind": "state", "value": "awake"|"sleeping"}` to the gui_queue on every real state transition; the orb only advances `_rotation_deg` while `_awake` is True, and speeds up (via the existing amplitude signal) while actively speaking. Verified for real, not assumed: captured two frames 1.5s apart while asleep (pixel-for-pixel workflow confirmed via screenshot - wedge positions identical) and two frames while awake (wedge positions visibly different) using the real `StatusOrb` instance, not a mock.
  - **Found and fixed a real bug while implementing "invisible on shutdown"**: reasoning through the threading model surfaced that `Orchestrator.run_forever()` finishing (a background daemon thread) would NOT stop `StatusOrb.run()`'s `mainloop()` (running on the main thread) on its own - the orb would keep running indefinitely after "shutdown" with no code change. Fixed by having the SHUTDOWN command explicitly push `{"kind": "shutdown"}` to the gui_queue (after the goodbye is spoken, so the orb is still alive to react to it), handled by calling `root.destroy()` from within the queue-polling callback (safe - it already runs on the Tk thread via `root.after()`). Verified for real: `orb.run()` correctly returns after the shutdown message, and a full real-orchestrator sleep -> wake -> sleep -> shutdown cycle (transcript controlled directly, since real "Vaayu" recognition remains a separately-tracked unresolved issue - not what this test targets) showed correct state transitions and the window closing at the end.

## Phase 2 (later, after Phase 1 is solid): Android Companion

Not built now — scoped here so Phase 1's `interfaces/remote_api.py` seam is designed with this in mind.

- **Capability level**: Accessibility Service (screen read + tap/type/swipe in any app) **+ Shizuku** (silent install/uninstall, programmatic permission grants) — no root. This was the user's explicit choice, rejecting full root due to banking-app breakage and Play Integrity maintenance burden.
- **Distribution**: personal sideload only (APK direct install / ADB), never Play Store — avoids Play policy restrictions on SMS/Accessibility that only apply to publicly distributed apps. Note Android 13+ requires one extra "Restricted settings → allow" tap for sideloaded Accessibility grants; Google's "Advanced Protection Mode" must stay off on this phone since it blocks non-Play Accessibility grants entirely.
- **Dual-mode brain — independent of the PC, not just a remote control**: the user chose full phone independence over a PC-dependent remote-control model. Two brain paths, selected automatically by connectivity/PC availability:
  - **Connected mode**: when the PC assistant is reachable on the local network, the phone forwards commands to the PC's Ollama-backed 7B-class brain (stronger reasoning) over local HTTP/websocket — same tool-registry/confirmation-gate design, no duplication.
  - **Standalone mode**: when the PC is off/unreachable, the phone falls back to an **on-device model** via a mobile-native inference runtime (`llama.cpp` for Android, or MLC-LLM) — NOT Ollama, which doesn't run on Android at all. Model choice: a small quantized model in the 1-3B range (e.g. Llama 3.2 1B, Qwen2.5 1.5B). This model is too large to silently bundle in the APK (several hundred MB–~2GB); it downloads once on first launch (user-confirmed, over Wi-Fi) and is cached locally for fully offline use afterward.
  - **Known trade-off to set expectations on**: the standalone on-device model is noticeably weaker at command understanding and tool selection than the PC's 7B model — more misunderstood commands should be expected in standalone mode. This is a real limitation, not a bug to fix later.
- **Same permanent safety rule carries over**: any Android tool touching finance/payment apps, credentials, 2FA, or sending communications must be `requires_confirmation=True`, regardless of which brain path handled the request.
